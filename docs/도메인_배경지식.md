# 배터리팩 용접설비 예지보전 — 도메인 배경지식

이 문서는 도메인 지식(제조/설비/예지보전) 없이 이 프로젝트에 들어온 사람을 기준으로,
"왜 이런 데이터를 이런 방식으로 분석하는가"를 개념적으로 정리한 참고 문서입니다.
`notebooks/00_가이드북_요약.ipynb`가 KAMP 가이드북의 내용을 요약한 것이라면, 이 문서는
그 내용을 이해하는 데 필요한 **배경 개념**을 보충합니다. 분석이 진행되면서 계속 업데이트해
나가는 것을 전제로 작성했으며, 맨 아래에 업데이트 로그를 둡니다.

---

## 1. 예지보전(Predictive Maintenance)이란 무엇인가

설비를 관리하는 방식은 보통 세 단계로 발전해왔습니다.

| 방식 | 언제 손보나 | 비유 |
|---|---|---|
| 사후보전 (Reactive) | 고장이 난 뒤에 고친다 | 자동차가 완전히 멈춘 뒤 정비소에 간다 |
| 예방보전 (Preventive) | 정해진 주기마다 미리 교체/점검한다 (고장 여부와 무관) | "5,000km마다 엔진오일 교체"처럼 시간/사용량 기준 |
| 예지보전 (Predictive) | 설비의 실제 상태(신호)를 계속 지켜보다가, 고장 조짐이 보일 때 손본다 | 계기판 경고등이 뜨기 시작하면 그때 점검한다 |

예방보전은 안전하지만 낭비가 많습니다 (멀쩡한 부품도 주기가 되면 교체). 예지보전은 설비가
실제로 "이상해지는 조짐"을 데이터로 포착해서, 딱 필요한 시점에만 개입하는 것을 목표로 합니다.
그러려면 "설비가 정상일 때 어떤 신호를 내는지"를 먼저 정의할 수 있어야 하고, 그 기준에서
벗어나는 순간을 실시간으로 감지할 수 있어야 합니다. 이 프로젝트가 다루는 문제가 정확히 이것입니다 —
레이저 용접설비가 찍어내는 RealPower(실제 용접 출력) 신호를 계속 관찰하다가, 정상 패턴을 벗어나면
"이상 조짐"으로 판단하는 시스템을 만드는 것입니다.

> **왜 하필 "예측 오차"로 이상을 판단할까?**
> 설비가 정상일 때는 다음에 나올 값을 어느 정도 예측할 수 있습니다 (용접 사이클이 반복되니까요).
> 설비에 문제가 생기면 그 예측이 갑자기 틀리기 시작합니다. 즉 "예측이 틀리는 정도"가 곧
> "설비가 평소와 달라진 정도"의 대리 지표가 되는 것입니다. 이것이 이 프로젝트가 시계열
> 예측 모델(N-HiTS)을 이상탐지에 쓰는 이유입니다.

## 2. 왜 "정상 데이터만" 학습하는가 (비지도 이상탐지)

일반적인 머신러닝 분류 문제는 "정상 예시"와 "불량 예시"를 둘 다 충분히 모아서 그 차이를
학습시킵니다. 하지만 제조 현장에서는 불량이 자주 나지 않기 때문에(그래야 정상이죠) 불량
샘플을 충분히 모으기가 어렵고, 불량의 유형도 매번 다를 수 있습니다.

그래서 이 프로젝트는 반대로 접근합니다 — **"정상이 어떻게 생겼는지"만 아주 많은 데이터로
확실하게 학습**해두고, 그 정상 패턴에서 벗어나는 모든 것을 "이상 후보"로 취급합니다. 이런
접근을 비지도 이상탐지(unsupervised anomaly detection)라고 부릅니다. `Training_Data.csv`에
불량 라벨이 아예 없는 이유가 이것입니다 — 애초에 정상 데이터로만 구성되어 있고, 이 데이터로
"정상이란 무엇인가"의 기준을 세우는 데 씁니다. 반대로 테스트셋에는 정상 2개, 비정상 2개를
섞어두고 실제 라벨을 붙여서, 우리가 세운 "정상 기준"이 새로운 데이터에서도 잘 작동하는지
검증합니다.

## 3. 이 데이터가 나오는 현장: 배터리팩 제조와 레이저 용접

전기차/전기버스용 배터리팩은 크게 3단계를 거쳐 만들어집니다.

1. **배터리셀 검사/조립** — 낱개 셀을 OCV(개방전압), 절연저항, 내부저항으로 검사해 양/불 판정
2. **배터리모듈 조립** — 여러 셀을 모아 하나의 모듈로 만듦. 조립 자체는 사람이, **용접은 설비가 자동으로** 수행
3. **배터리팩 조립** — 완성된 모듈들을 케이스에 넣고 충·방전 시험 후 출하

이 프로젝트가 보는 것은 2단계의 **레이저 용접 공정** 하나입니다. 이 공정이 특별히 예지보전
대상으로 뽑힌 이유는, 용접 앞단(모듈을 용접 가능한 형태로 조립해 설비에 넣는 과정)이
사람 손으로 이루어진다는 데 있습니다. 그래서 불량이 나왔을 때 "설비 자체가 이상했던 건지"
"사람이 조립을 잘못 넣었던 건지"를 구분하기가 어렵습니다. 용접설비가 찍어내는 신호(RealPower 등)만
따로 떼어서 감시할 수 있으면, 이 둘을 분리해서 볼 수 있는 첫 번째 단서를 얻게 됩니다.

### 데이터는 어떻게 설비에서 여기까지 왔나 (AAS 수집 체계, 개념만)

공장 설비 데이터를 다룰 때 자주 나오는 용어들을 아주 간단히 정리하면:

- **PLC** (Programmable Logic Controller): 설비를 직접 제어하는 산업용 컴퓨터. 용접 타이밍,
  출력 등을 여기서 결정합니다.
- **OPC UA**: 서로 다른 회사의 설비/소프트웨어가 데이터를 주고받기 위한 공통 통신 규격.
- **AAS** (Asset Administration Shell): "이 설비가 어떤 데이터를, 어떤 이름으로, 어떤 주기로
  내보내는지"를 표준화된 형식으로 정의해두는 산업 디지털트윈 표준. 이 프로젝트의 `AASX 및 변환파일/`
  폴더가 바로 이 정의 파일입니다.
- **TSDB** (Time-Series Database): 시간에 따라 계속 쌓이는 데이터를 저장하기 위한 전용
  데이터베이스. 여기서 우리가 쓰는 CSV로 값을 뽑아옵니다.

즉 "PLC가 만든 값 → OPC UA로 전송 → AAS 표준에 맞춰 태그 매핑 → TSDB에 저장 → CSV로 추출"
이라는 파이프라인을 거쳐 `Training_Data.csv` 같은 파일이 만들어진 것입니다. 우리가 직접 이
파이프라인을 구축할 일은 없지만, "이 데이터가 실시간 설비 신호를 표준화된 방식으로 받아온
것"이라는 맥락은 데이터를 해석할 때 도움이 됩니다 — 예를 들어 결측치나 이상치가 거의 없는
이유도, 이미 정형화된 수집 체계를 거쳤기 때문입니다.

## 4. 변수들이 실제로 무엇을 의미하는가

| 변수 | 도메인적 의미 |
|---|---|
| RealPower | 용접 포인트에서 **실제로 나간** 출력. 예지보전의 핵심 관찰 대상입니다. |
| SetPower | 용접기에 **설정된** 목표 출력(%). RealPower가 이 설정값에 잘 맞춰 나왔는지가 "정상 용접"의 기준입니다. |
| GateOnTime | 용접을 위해 게이트(출력을 내보내는 스위치 역할)가 열려있던 시간. 길수록 더 오래 에너지를 쏟은 것. |
| Speed, Length | 용접 헤드가 움직이는 속도·거리 설정. 용접 부위의 물리적 형태를 결정. |
| PageNo | 하나의 모듈 안에서 몇 번째 용접 포인트인지 (순번). |
| WorkingTime | 그 용접이 실제로 발생한 시각. |

가장 중요한 관계는 **RealPower ≈ 2000 × SetPower(%)** 라는 점입니다. 예를 들어 SetPower가
83%로 설정되면 RealPower는 이론상 1,660W 근처가 나와야 정상입니다. EDA에서 RealPower의
분포가 두 개의 봉우리(약 700W대, 약 1700W대)로 갈라져 보였던 이유도 이것입니다 — 이 설비가
쓰는 SetPower 값 자체가 38%, 82%, 83% 몇 가지로 정해져 있어서, 정상 운전 중에도 원래
여러 그룹으로 나뉘어 보이는 것입니다. 그래서 "RealPower가 낮다/높다"만으로는 이상을 판단할 수
없고, **"그 시점의 SetPower 설정을 기준으로 RealPower가 기대 범위 안에 있는가"**를 봐야
합니다. 가이드북에서 허용 오차를 2000의 3~4%(약 ±60~80) 이내로 잡은 것도 이런 맥락입니다.

## 5. 이 프로젝트가 쓰는 두 가지 이상탐지 전략 (개념)

같은 "이상"이라도 나타나는 모양이 다르면 잘 잡아내는 방법도 다릅니다. 이 프로젝트는 두 가지
서로 다른 이상 패턴을 구분해서 다룹니다.

### 5.1 고립형 이상 — "가끔 한 번씩 튀는 값" → 예측 기반 탐지 (N-HiTS)

> **비유**: 심전도를 계속 관찰하다가, 평소 리듬과 다른 박동이 한 번 튀어나오면 바로 알아채는 것과
> 비슷합니다. 평소 리듬(패턴)을 알고 있어야, "이건 평소와 다르다"는 판단이 가능합니다.

N-HiTS는 시계열 예측 모델입니다. "지금까지 20개 구간을 보면, 다음 10개 구간은 대략 이런
값이 나올 것이다"를 정상 데이터로 학습해둡니다. 학습이 끝난 모델에 새로운(테스트) 데이터를
흘려보내면서, 모델이 예측한 값과 실제 값의 차이(오차)를 계속 계산합니다. 설비가 정상이면 이
오차는 작고 일정한 범위 안에 머무릅니다. 그런데 특정 시점에서 설비가 순간적으로 이상 동작을
하면, 그 지점의 실제값이 모델의 예측에서 크게 벗어나 오차가 튑니다. 이 오차를 표준화한 값이
Z-score이고, 이게 threshold(예: 4.0)를 넘으면 "이 시점은 이상"이라고 판정합니다.
`WeldingTest_03_NG.csv`가 이런 유형입니다 — 대부분 정상이다가, 몇몇 고립된 시점에서만
튀는 패턴입니다.

### 5.2 N-HiTS "잔차 점수(Residual Score)"란 정확히 무엇인가

5.1에서 "예측한 값과 실제 값의 차이(오차)"라고 뭉뚱그려 말한 부분을, `03_nhits_model.ipynb`에서
실제로 계산하는 방식 그대로 조금 더 자세히 풀어보면 다음과 같습니다.

> **비유**: 어떤 사람이 매일 몇 시에 퇴근하는지 예측하는 모델이 있다고 해봅시다. 평소엔 예측이
> ±10분 정도 빗나가는 게 "정상적인 흔들림"입니다. 그런데 어느 날 예측보다 3시간이나 늦게
> 퇴근했다면, 중요한 건 "3시간이라는 차이" 그 자체가 아니라 **"평소 흔들림(±10분)에 비해 몇 배나
> 벗어났는가"**입니다. 잔차 점수가 바로 이 "평소 대비 몇 배 벗어났는가"를 숫자 하나로 나타낸
> 것입니다.

**① 잔차(residual) = 실제값 − 예측값, 그것도 "한 스텝 뒤"만**

N-HiTS는 원래 최근 20개 구간(encoder)을 보고 앞으로 10개 구간(decoder)을 한 번에 예측하는
모델입니다. 그런데 이 프로젝트는 "원본 데이터 한 행마다 이상 여부를 하나씩 판정"해야 하므로,
10개짜리 예측 묶음 중 **바로 다음 한 스텝(1-step-ahead)의 예측값만** 골라 씁니다. 그래야
윈도우가 겹치는 구조에서도 예측값 하나와 실제 시점 하나를 1:1로 정확히 대응시킬 수 있습니다
(`one_step_residuals` 함수가 하는 일이 바로 이 정렬입니다). 이렇게 얻은
`잔차 = 실제값 − 예측값`이 "그 시점에서 모델이 얼마나 예측을 틀렸는가"의 원재료입니다.

**② 잔차를 표준화 — "정상일 때는 원래 이 정도 흔들린다"는 기준 세우기**

잔차 값 자체(예: 12.3W)는 그대로는 판단 기준이 되기 어렵습니다. RealPower처럼 값의 스케일이
큰 신호에서는 "12.3만큼 틀렸다"가 큰 건지 작은 건지 알 수 없기 때문입니다. 그래서 **학습에
쓰지 않은 정상 데이터 구간(검증 구간)**에서 잔차들을 모아 평균(RESID_MU)과 표준편차
(RESID_SIGMA)를 구합니다 — 이것이 "정상 상태에서는 예측이 보통 이 정도 크기로, 이 정도
흔들리며 틀린다"는 기준선입니다.

**③ 잔차 점수(z-score) 계산과 판정**

새로운(테스트) 시점의 잔차를 이 기준으로 표준화한 값이 잔차 점수입니다.

```
잔차 점수(z) = (그 시점의 잔차 − RESID_MU) / RESID_SIGMA
```

`|z|`가 threshold(예: 4.0)를 넘으면 "정상적인 흔들림으로는 설명되지 않을 만큼 예측이 크게
빗나갔다"고 보고 그 시점을 이상(1)으로 판정합니다. 즉 잔차 점수는 "이 시점이 정상 흔들림 대비
몇 배(몇 표준편차)나 벗어났는가"를 뜻하는, 단위 없는 표준화된 이상 정도 지표입니다.

**④ 이 방식의 한계 — 실제로 확인된 내용**

잔차 점수는 RealPower(전력) 시계열 **하나만** 보고 계산됩니다. SetPower(설정값) 같은 다른
컬럼의 정보는 전혀 반영하지 않습니다. 그 결과:

- `WeldingTest_04_NG.csv`처럼 RealPower 값 자체가 크게 벗어나는 이상은 잔차 점수가 잘
  잡아냅니다 (F1 ≈ 0.97, 3장 참고).
- 반면 `WeldingTest_03_NG.csv`의 이상은 대부분 "설정값 자체가 훈련 데이터에 없던 값
  (SetPower=35)"이라서 생기는데, 이때 RealPower 흐름 자체는 정상 범위 근처에서 크게 튀지
  않는 경우가 많아 잔차 점수만으로는 잘 잡히지 않습니다 (Precision ≈ 0.19 수준, threshold=4
  기준). SetPower를 직접 보는 베이스라인(6~7장, `02_baseline_zscore.ipynb`)이 이 유형의
  이상을 훨씬 잘 잡아내는 이유가 여기 있습니다.

정리하면, 잔차 점수는 "지금까지의 흐름으로 미루어 볼 때 이 값이 나올 만했는가"를 판단하는
데는 강하지만, 애초에 모델에 보여주지 않은 변수(SetPower)가 원인인 이상에는 눈이 멀어
있습니다. 어떤 신호를 모델에 입력으로 줄지 자체가 탐지 성능을 좌우한다는 것을 보여주는
사례입니다.

### 5.3 연속형 이상 — "설비 자체가 다른 상태로 넘어감" → 통계분포 기반 탐지 (Z-score)

> **비유**: 반 전체 학생의 평균 키 분포를 알고 있는 상태에서, 어떤 학생의 키가 그 분포에서
> 한참 벗어나 있으면 "또래와 다르다"고 판단하는 것과 비슷합니다. 여기서는 "어떤 시점의 값이
> 정상 분포에서 얼마나 벗어나 있는가"를 매 순간 독립적으로 판단합니다.

`WeldingTest_04_NG.csv`처럼 **특정 시점 이후로 아예 다른 상태가 지속**되는 경우는 예측
모델 방식이 오히려 불리할 수 있습니다 — 비정상 상태가 오래 지속되면 모델이 "어? 요즘은 계속
이 값이네" 하고 그걸 새로운 정상으로 착각하며 적응해버릴 위험이 있기 때문입니다. 그래서 이런
경우엔 예측 대신, 정상 학습 데이터의 통계적 분포(RealPower가 정상일 때 어떤 평균/표준편차를
갖는 몇 개의 그룹으로 나뉘는지)를 미리 구해두고, 새로운 값 하나하나가 그 분포에서 얼마나
멀리 떨어져 있는지를 매번 독립적으로 비교합니다. 시간의 흐름(문맥)에 기대지 않기 때문에, 이상
상태가 아무리 오래 지속돼도 "정상 분포에서 여전히 멀다"는 판단이 계속 유지됩니다.

### 5.4 왜 하나로 통일하지 않고 두 개를 같이 쓰는가

두 방법은 서로 다른 가정 위에 서 있습니다. N-HiTS는 "바로 직전 문맥(시간 흐름)"을 이용해서
다음 값을 예측하는 데 강하고, 통계분포 방식은 "문맥과 무관하게 값 자체가 정상 범위에
있는가"를 보는 데 강합니다. 실제 현장에서는 이상이 어떤 모양으로 나타날지 미리 알 수 없기
때문에, 두 방법을 함께 돌려서 서로의 약점을 보완하는 것이 일반적인 전략입니다. 이건 이
프로젝트만의 특징이 아니라, 시계열 이상탐지 전반에서 자주 쓰이는 조합입니다.

## 6. 탐지 성능을 어떻게 평가하는가 (Accuracy / Precision / Recall / F1)

이상탐지 결과는 결국 "각 시점을 정상(0)/이상(1)으로 맞혔는가"의 문제로 귀결되고, 다음 네
지표로 평가합니다.

| 지표 | 의미 | 예지보전 맥락에서의 의미 |
|---|---|---|
| Accuracy (정확도) | 전체 중 맞춘 비율 | 이상이 워낙 드물게 나오므로, 이 지표만 보면 "다 정상이라고만 해도" 높게 나올 수 있어 **단독으로는 신뢰하기 어렵습니다.** |
| Precision (정밀도) | "이상"이라고 판단한 것 중 실제로 이상이었던 비율 | 낮으면 오탐(false alarm)이 잦아 현장 신뢰를 잃습니다. |
| Recall (재현율) | 실제 이상 중 놓치지 않고 잡아낸 비율 | **예지보전에서 가장 치명적인 실패는 이상을 놓치는 것(False Negative)** 입니다. 불량이 그대로 다음 공정까지 흘러가기 때문입니다. |
| F1-score | Precision과 Recall의 조화평균 | 둘 사이의 균형을 한 숫자로 요약. |

가이드북 결과에서 `WeldingTest_03_NG`(고립형)는 Precision·Recall 모두 0.8947, F1 0.8947,
`WeldingTest_04_NG`(연속형)는 전부 1.0이 나왔습니다. 같은 모델(조합)이라도 이상의 "모양"에
따라 잡아내는 난이도가 다르다는 것을 보여주는 결과입니다.

| 시계열 (Time Series) | 시간 순서를 가진 연속된 데이터 |
| N-HiTS | 시계열을 여러 시간 스케일로 나눠 예측한 뒤 합치는 딥러닝 예측 모델 |
| 잔차 (Residual) | 실제값 − 예측값. 모델이 그 시점을 얼마나 못 맞혔는지를 나타내는 원값 (5.2 참고) |
| 잔차 점수 (Residual Score) | 잔차를 정상 구간 잔차의 평균/표준편차로 표준화한 z-score. N-HiTS 이상탐지의 핵심 판정 지표 (5.2 참고) |
| Z-score | 어떤 값이 평균에서 표준편차 몇 배만큼 떨어져 있는지를 나타내는 표준화 지표 |
| IQR (사분범위) | Q3(75%지점)-Q1(25%지점). 이상치 판별에 흔히 쓰임 |
| Threshold | 정상/이상을 가르는 기준값 |
| AAS (Asset Administration Shell) | 설비/자산의 데이터를 표준화된 형식으로 정의하는 산업 디지털트윈 표준 |
| OPC UA | 산업 설비 간 데이터 통신을 위한 표준 프로토콜 |
| PLC | 설비를 직접 제어하는 산업용 컴퓨터 |
| TSDB | 시계열 데이터 전용 저장소 |
| OCV (개방전압) | 배터리셀에 부하가 없을 때의 전압. 셀 상태 판정 기준 중 하나 |
| BMS (Battery Management System) | 배터리 상태를 감시·관리하는 시스템 |
| Precision / Recall / F1-score | 분류·탐지 성능을 평가하는 표준 지표 (위 6장 참고) |
